# CLAUDE.md

OceanBlock is a fork of one-block; its design lives in `docs/superpowers/specs/2026-10-18-oceanblock-design.md`. Rename rule: Kotlin packages are `ocean_block.*`, but Textura keeps `one_block.textura` (and every `one_block.textura.*` import) and the literals `"oneblock"`, `oneblock:gui`, `oneblock.admin` and `oneblock_level` are preserved.

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

This is a Gradle multi-module monorepo (Kotlin/JVM 2.3.0, JDK 25 toolchain, Paper 26.3). The shippable artifact is the `ocean-block` Paper plugin, assembled by shading many internal modules into one jar.

**Primary build+deploy command** (builds the shaded jar and copies it into `server/plugins/`):

```bash
./gradlew :plugins:oceanblock:plugin:localDeploy
```

- `localJar` / `localDeploy` come from the `paper-plugin` convention. `productionJar` builds the prod jar into `build/libs` only.
- The dev server (Paper) must be **stopped** before deploying — Windows locks the running jar and the copy fails. `localDeploy` intentionally does not track state (its destination `server/plugins/` holds other plugins' runtime data, e.g. LuckPerms' H2 DB).
- After deploying, the server must be **restarted** (or the plugin reloaded) to pick up the new jar.

### The `isLocal` mechanism — read before running any Gradle task

The build mode is derived from whether **any requested task name contains the substring `local`** (case-insensitive), via `gradle.startParameter.taskNames`. This flag (`isLocal`) changes dependencies and source sets in `plugins/oceanblock/plugin` and `lib/connection`:

| | local mode (task name has "local") | production mode (anything else) |
|---|---|---|
| `com.redescreen:sdk:1.0` | skipped | required (**only exists in the prod environment**) |
| MongoDB driver | `implementation` (shaded) | `compileOnly` |
| `lib:connection` source | `src/local/kotlin` | `src/production/kotlin` |

`lib:connection` additionally accepts `-Penv=local` as an override, so `./gradlew :lib:connection:build -Penv=local` works; the plugin module honors task names only.

Consequence: a plain `./gradlew build`, `test`, or `:some:module:compileKotlin` runs in **production mode** and fails resolving `com.redescreen:sdk:1.0`. Always drive local work through a `local*` task. To compile everything locally, `:plugins:oceanblock:plugin:localDeploy` transitively builds all modules.

### Local dependency jars (not on any repo)

Three paths are wired as file dependencies and must exist on disk or the build fails with unresolved symbols rather than a dependency error:

- `jars/inventory-framework-paper-3.7.1.jar` — inventory-framework, `compileOnly` for every module via `paper-common`, `implementation` (shaded) in both plugin modules. The version catalog entry `inventoryFramework` is unused.
- `jars/ModelEngine-4.1.0.jar` — ModelEngine (`com.ticxo.modelengine.api`), `compileOnly` by `system/spawn` only (NPC models). A runtime `softDepend`, so `NpcModel.isAvailable()` gates every call and NPCs fall back to a non-model presentation without it.
- `.dep/` — a `fileTree` of server-only APIs (currently `SkinsRestorer.jar`), consumed `compileOnly` by `system/islands`.

`jars/packetevents-spigot-2.13.0.jar` is **not** one of them — packetevents resolves from Maven (`repo.codemc.io`) via the `packetevents-spigot` catalog entry. That jar is just the copy you drop into `server/plugins/`; it is a runtime `softDepend`, so the build succeeds without the server plugin but `lib:toast` silently no-ops (logs once) if PacketEvents is missing at runtime.

### Tests

Tests use **Kotest 5.9 on the JUnit 5 platform**. `paper-common` does *not* wire testing — a module that wants tests must add `testImplementation(libs.kotest.runner)` + `libs.kotest.assertions` (plus `libs.paperApi` when the code under test touches Bukkit types) and `tasks.test { useJUnitPlatform() }` to its own `build.gradle.kts`. Only `plugins/textura`, `system/custom-items`, `system/islands`, `system/drift`, `system/craft`, `system/stations` and `system/research` have tests today; `system/research` depends on `lib:connection`, so it also has a `localTest` alias. Tests live under `src/test/kotlin`.

```bash
./gradlew :plugins:oceanblock:system:custom-items:test
./gradlew :plugins:textura:localTest
./gradlew :plugins:textura:test --tests "*CooldownStore*"
```

`plugins/textura` also registers a `localTest` alias whose only purpose is to put `local` in the task name so the build resolves in local mode. Modules that do **not** depend on `lib:connection` test cleanly. A whole-project `test` fails in production mode on the `com.redescreen:sdk` resolution unless that SDK is present.

## Architecture

### Convention plugins (`build-logic/`)

- **`paper-common`** — base for every module: Kotlin + Shadow, paper-api (`26.3.build.192-stable`, Adventure 5 — `ClickEvent<T>` is generic and `net.kyori.examination` is gone, so Textura shades and relocates it for `creative`) and the local inventory-framework jar as `compileOnly`, Aikar ACF (`co.aikar:acf-paper`) as `implementation`, JDK 25, Shadow 9.2.2 (9.3+ needs a newer Gradle; 8.x cannot read Java 25 classes), and the full list of third-party Maven repos. Every module (including `lib:*` and `system:*`) produces a shadowJar with an empty archive classifier.
- **`paper-plugin`** — applies `paper-common` + `plugin-yml.bukkit`, disables the thin `jar` task (it would collide with shadowJar on the same output name), and adds `localJar` / `productionJar` / `localDeploy`. Only the two real plugins apply it. Because the thin `jar` is disabled, the convention also republishes `shadowJar` into `apiElements`/`runtimeElements`: without that, a project that applies `paper-plugin` has **no consumable artifact**, and `compileOnly(projects.plugins.textura)` in `lib:formatter` resolves to nothing — it only compiles while a stale jar happens to sit in `build/libs`, and fails on any clean build.

### Two shippable plugins vs. shaded modules

Only `:plugins:oceanblock:plugin` and `:plugins:textura` are standalone plugin jars. **All `:lib:*` and `:plugins:oceanblock:system:*` modules are shaded into the ocean-block jar** — the plugin module `implementation`s every `:plugins:oceanblock:system:*` and `:lib:*` and merges them at `shadowJar` time. `textura` is a separate jar declared in ocean-block's `depend` list (`PlaceholderAPI`, `SkinsRestorer`, `Textura`), not shaded — systems that need it (e.g. `islands`) take `compileOnly(projects.plugins.textura)` and resolve it at runtime from the server.

### System module pattern

Each feature lives in its own module under `plugins/oceanblock/system/<name>/` and exposes a singleton `object <Name>System` with an `init(...)` function. `OceanBlockPlugin.onEnable()` wires everything in three phases:

- `setupSystems()` — calls every `XxxSystem.init(plugin, viewFrame | paperCommandManager)`.
- `setupCommands()` — registers Aikar ACF commands via `PaperCommandManager` (`@CommandAlias`, `@Subcommand`, `@Default`, `@CommandPermission`).
- `setupListeners()` — registers Bukkit `Listener`s.

To add a feature module: register it in `settings.gradle.kts`, add it to the plugin's dependency loop (systems under `:plugins:oceanblock:system:` are auto-included), and call its `init` in `setupSystems()`. Those two steps are independent — a module can be included and shaded without being `init`ed. Check `setupSystems()` before assuming a module under `system/` is live.

Systems may `compileOnly` on other systems to register into them (e.g. `drift` depends on `custom-items` and calls `CustomItemRegistry.register(GanchoItem)` from its own `init`, and on `islands` for island lookups). Keep that registration inside the depending system's `init`, not in the plugin module.

#### Custom-item framework (`system/custom-items`)

Reusable in-game item behavior lives here — do **not** hand-roll per-item click listeners in other modules. Define a behavior by subclassing `CustomItem` (`api/CustomItem.kt`): override the appearance fields (`id`, `material`, `displayName`, `lore`, `itemModel`, `cooldownMillis`, `heldTickInterval`) and the hooks you need (`onRightClick`, `onLeftClick`, `onInteractEntity`, `onConsume`, `onHeldTick`; plus optional `listeners()` / `tasks()`). `build()` stamps the `id` into item NBT under `CustomItemKeys.ID`; `CustomItemRegistry.fromItemStack(...)` resolves an `ItemStack` back to its `CustomItem` by that tag. Register built-ins in `CustomItemSystem.registerBuiltInItems()` (e.g. `MultiToolItem`). A single global tick task in `CustomItemSystem` drives every item's `onHeldTick` at its own `heldTickInterval`; a shared `CooldownStore` gates activations.

#### Starting island (`system/islands`)

The player starts on an island pasted from a schematic, not a raft. `StarterIsland.generate` (called by `IslandManager.createIsland` and `IslandResetService.resetTerrain`) pastes `server/plugins/ocean-block/templates/island.schem` (tracked in git) asynchronously through FAWE with `ignoreAirBlocks(true)`, clipboard origin at `(lot center X, IslandPlacement.PASTE_Y = 64, lot center Z)`. The schematic was copied standing at Y 64 on the island center. Its bounding box is 18×25×16 (offset -8, -13, -7), but the solid island is only about 11×11 (X/Z -4..+6 from the center) and spans Y 54–75, with the ground at Y 63. `IslandPlacement.center` is Y 63 (`GROUND_Y`) and `IslandPlacement.spawn` is the center block + 0.5 at Y 64. A missing schematic or a failed paste logs `[ilha]` at severe and places the main-thread fallback: 3×3 `GRASS_BLOCK` at Y 63 over `DIRT` at Y 62. `generate(island, onReady)` (and `IslandManager.createIsland(player, onReady)`) invoke `onReady` on the main thread once the paste completes or the fallback is placed (immediately if the world is not loaded; synchronously when the schematic is missing). Anything that teleports a player onto a fresh or reset island must do it inside `onReady`, never right after the call: the `/ilha` default command, the first-join auto-create in `PlayerListener`, the spawn portal and `resetTerrain` all do. Every teleport onto the island targets `spawn + (0, 2, 0)`; `spawn` already holds the +0.5 block center. Player-facing text says "ilha" (feminine: "sua ilha"); the command is `/ilha` (aliases `island`, `is`). There is no island HUD any more (the old `IslandHud` bossbar and `SpawnHudListener` were removed on 2026-10-19); on-screen feedback goes through Textura notifications.

#### Drift and hook (`system/drift`)

Debris floats past each active island and the player pulls it in for materials. `DriftSystem.init(plugin, viewFrame)` runs after `IslandsSystem` and `CustomItemSystem`, and `DriftSystem.onDisable()` must stay in `OceanBlockPlugin.onDisable()`: it cancels the tasks and removes every tracked display.

- **Config (`config/`)**: `DriftFile.load` copies the bundled `drift.yml` to `server/plugins/ocean-block/drift.yml` when missing and hands it to `DriftConfigParser`, which clamps bad numbers to a default (with a warning) and skips invalid types/drops/materials (logged, never fatal). No valid type means a `severe` log and drift off; the rest of the plugin keeps working. Keys: `corrente` (`direcao` EAST/WEST/SOUTH/NORTH, `velocidade`, `comprimento`, `largura`, `largura-minima`, `altura`, `riscos`, `riscos-por-segundo`), `spawn` (`intervalo-ticks`, `maximo-por-lote`, `tempo-preso-segundos`), `animacao` (`balanco`, `periodo-balanco-ticks`, `inclinacao-graus`, `giro-graus-por-segundo`, `sinuosidade`, `periodo-sinuosidade-ticks`, `variacao-velocidade`, `rastro`), `obstaculo` (`profundidade-maxima`, `velocidade-mergulho`, `tempo-sumir-ticks`), `coleta` (`raio-gancho`, `raio-toque`), `rede` (`raio`), `detritos.<id>` (`peso`, `exibicao`, `escala`, optional `afundamento`, `drops` with `material/min/max/chance`). Units: `velocidade` is blocks per tick, lengths/radii/`altura` are blocks, intervals are ticks except `tempo-preso-segundos`. **`largura` and `largura-minima` are half-widths**: the lateral spawn offset (`DriftLane.lateralOffset`) has a magnitude uniform in `[largura-minima, largura]` and a random sign, so debris passes alongside the island shore on either side and never down its middle (defaults 8 and 13; the solid island reaches about 6 blocks from the center, so debris passes 2–7 blocks off the shore). `largura-minima` is clamped to `0..largura` with a warning; 0 restores the old full band `[-largura, +largura]`. The current streaks use the same offset. The config is read once in `init`; editing `drift.yml` needs a restart.
- **Lanes (`lane/`)**: `DriftLane` is pure geometry. A lot's lane is centered on the island's center block (origin + 0.5) and `comprimento` long along the current; debris spawns at the upstream end with a lateral offset and is dropped once past the downstream end.
- **Debris (`debris/`)**: `DebrisManager` owns two global `BukkitTask`s (spawn every `intervalo-ticks`, move every 2 ticks) and the list of live `Debris` (a non-persistent `ItemDisplay` with `teleportDuration = 2`). A lot is active only while an online player stands inside it (`IslandManager.getIslandAt`); the next move tick removes all debris of a lot that is inactive or no longer exists. `BlockProbe` classifies each block as **solid** (`isSolid`, via `DebrisRules.isPassable = !isSolid`; checked first, so a waterlogged slab is solid), **water** (`WATER`, `BUBBLE_COLUMN`, `KELP`, `KELP_PLANT`, `SEAGRASS`, `TALL_SEAGRASS` or waterlogged) or **air**. Depths count down from `raftY = floor(altura)` (Y 62, the sea surface; the identifier predates the island). A debris is in one of three `Support` states (pure rules in `GravityRules`, Bukkit side in `DebrisFall`):
  - **Floating** (`DebrisDive`, pure rules in `DiveRules`): it drifts at the water surface of its column (`altura - depth - afundamento + bob`, the old height with a normal sea). If the next column's block at its level is solid, it **dives**: it picks the shallowest depth up to `obstaculo.profundidade-maxima` that is water at the next position and reachable through water in its current column (never through air), sinks or rises there at `velocidade-mergulho` without advancing, travels at `floor(altura) - depth + 0.5` with 30% bob and bubbles instead of the wake, and resurfaces once the surface ahead and the column above are water. If both that block and the next column's block at its current rendered height (`floor(levelY)`, which differs mid-dive) are air, it advances and starts falling; this check keeps a rising or sinking debris from clipping into a block. If its own block stops being water, it falls. The decision order (unloaded → unsupported → drop → dive target) is the pure `DiveRules.passage`. The dive search is capped at `min(max(profundidade-maxima, depth), profundidade-maxima + 4)`. Each column is classified at most once per step, through the per-step `ColumnKinds` memo.
  - **Falling**: item gravity (`vy -= 0.04; vy *= 0.98` per tick, capped at -1 block/tick), with no horizontal advance. Entering water makes it float and rise to that column's surface. Touching a solid block lands it **on the ground** at `top + 0.25·escala`, with no bob or spin. It is removed below `world.minHeight` or more than 64 blocks below `raftY`.
  - **On the ground**: still. Support is tested at the stored landed block (`landedTopY`), not at its rendered Y. Water returning there makes it float again, and losing the block underneath makes it fall. `escala` is clamped to 0.1..2.0.
  With no dive passage it is stuck. The stuck clock clears only when the debris actually advances along the lane (or starts falling or floating again), not while it holds mid-dive. Stuck and grounded debris both run the stuck clock: after `tempo-preso-segundos` the debris fades out (sinks 0.5 block and shrinks to scale 0 over `tempo-sumir-ticks`) and is removed. Stuck, grounded and falling debris can still be touched and hooked; only fading debris cannot. **Debris never force-loads chunks**: spawning is skipped, and a drifting debris is removed, when its target chunk is not loaded (`DebrisEntities.isLoaded`).
- **Floating animation**: `Debris.point` stays the straight base point on the lane; `DebrisPose` turns it plus `ageTicks` and the per-debris `FloatParams` (phases, spin direction, speed factor, rolled at spawn) into the rendered position (lateral meander, `y = levelY + bob`, where `levelY` is the surface/dive/fall height above) and a yaw/pitch/roll `leftRotation` interpolated over 2 ticks, all from the pure sine helpers in `FloatMotion`. The stuck check and lane end use the rendered x/z; `DebrisParticles` draws the wake behind each free debris every 10 ticks and the `FISHING` current streaks per active lot (loaded chunks only).
- **Collecting (`collect/`, `hook/`)**: by touch (`raio-toque`) or by reeling in the Gancho (nearest free debris within `raio-gancho` of the hook, pulled to the player over 10 ticks). `CollectorRule` allows owner, members and trusted names only; everyone else gets nothing, not even a message. `DebrisDelivery.deliver` is the single delivery path: inventory first (leftovers drop at the feet), pickup sound, splash particles, and a `CollectNotifier` notification in the Textura region `coleta` (item icon + `+N <item>`, 60 ticks, key `coleta:<MATERIAL>`; `CollectTally` sums repeated pickups of the same item while the line is alive). A net that becomes full sends `Sua Rede de Detritos ficou cheia!` with the loom icon to the island's online players in the region `avisos` (`NetFullNotifier`, once per fill, re-armed through `PlacedBlock.notifiedFull` when the net has a free slot again). `DriftSystem.init` registers the item icons of every drop material plus `loom` with `NotificationApi.registerItemIcons` during `onEnable`, before the startup pack build. `DropRoller` rolls each drop independently; a roll with no drops yields one `STRING`. The Gancho is a `CustomItem` (`GanchoItem`, a `FISHING_ROD`) registered in `CustomItemRegistry`, crafted only through the `craft` system (`DriftRecipes` registers it in `Recipes`, no vanilla recipe) and handed out by `FirstJoinListener` (`!hasPlayedBefore()`). `GanchoListener` only reads `PlayerFishEvent`, so vanilla fishing with it keeps working.
- **Debris net (`net/`)**: `NetBlock` is a `CustomBlock` (id `rede`, `LOOM`, `limitPerIsland = 4`, `storageCapacity = 27`) registered in `CustomBlockRegistry` from `DriftSystem.init` even when drift is off, crafted only through the `craft` system (`DriftRecipes`, no vanilla recipe) and handed out by `/cblock give rede`. A debris pull targets a sealed `PullTarget` (`Player(uuid)` for the Gancho, `Net(placedUuid)` for the net); both share the same 10-tick `stepToward` in `DebrisMotion`. After the touch check, every collectable debris asks `NetCatch.tryCatch` for the nearest non-full net of its own lot within `rede.raio` (3D distance from the rendered position to the block center, pure `NetRules.nearest`) and is pulled to block center + 0.5. On arrival `NetDelivery` puts the `DropRoller` drops into the net storage (leftovers are discarded, never dropped), `markDirty`s it and splashes at the block. If the net is gone, its chunk unloaded or it filled up mid-pull, the debris is discarded without delivery. `NetIndex` maps lot → `NetPoint`s (center, cached `full` from `NetRules.isFull`: no empty slot among the 27, even with partial stacks); it is rebuilt from `PlacedBlockManager.all()` every spawn tick and when a net is placed or broken, only from nets whose chunk is loaded, and one entry is refreshed after each delivery or withdrawal. `NetListener` runs at `LOW` before the framework's `CustomBlockListener`: it always denies the vanilla loom, and on a plain main-hand right click it cancels the event and opens `NetStorageView` only for `CollectorRule.canCollect` (others get nothing, not even a message). The view (27 slots plus `Coletar tudo`) only lets items out; each click re-reads the storage and the `requireAccess` guard (still registered, still a collector), so two viewers or a delivery mid-view never duplicate items. Withdrawals `saveNow` the block (a crash cannot hand back items already taken); deliveries only `markDirty`.
- **Seam for subproject 3**: debris type selection goes through `DebrisPool.typesFor(island)`; today `ConfigDebrisPool` returns every type from `drift.yml`. Per-phase pools replace that implementation, not the manager.
- **Testing limit**: the pure units (`DriftConfigParser`, `DebrisPicker`, `DropRoller`, `DriftLane`, `CollectorRule`, `FloatMotion`, `NetRules`, the arithmetic in `DebrisRules`, `DiveRules` and `GravityRules` with water/solid injected as lambdas) have Kotest tests. Rules that take a `Material` (`DebrisRules.isPassable` / `Material.isSolid`, `BlockProbe`) **cannot be unit-tested**: on Paper 26.3 `Material.isSolid` needs the server registry, absent in a plain JVM test. Only the manual checklist (section 7 of `docs/superpowers/plans/2026-10-18-oceanblock-aceite-manual.md`) covers them; do not "fix" that by mocking `Material`.

#### Recipes (`system/craft`)

OceanBlock recipes are crafted only through the `/receitas` dialog (aliases `/craft`, `/receita`; the spawn NPC "RECEITAS" runs `craft`). There are no vanilla crafting-table recipes for them and nothing from one-block's craft (`/forja`, leather/platinum, paxel recipes) remains.

- **Model (`recipe/`)**: `OceanRecipe(id, name, description, category, result: () -> ItemStack, ingredients)` grouped by the `RecipeCategory` enum (`FERRAMENTAS` `ui:pickaxe`, `COLETA` `ui:chest`, `PROCESSAMENTO` "Estações" `ui:sparkle`; the icon must be an alias in the `stone` theme's `icons:`). `Ingredient(label, amount, plural, icon) { matches }`, with `Ingredient.material(...)` / `Ingredient.tag(..., icon = ...)`; `icon` is the material shown in the card's ingredient slot (a tag needs it explicitly, e.g. `oak_planks`; a custom-item ingredient uses its base material), and an ingredient without one shows no slot. `labelFor(n)` picks singular or plural. Other systems register into the global `Recipes` book from their own `init` (drift: `DriftRecipes` adds Gancho, 3 Tábuas + 2 Linhas, and Rede de Detritos, 4 Tábuas + 5 Linhas); a duplicate id throws. `byCategory()` lists only categories with recipes, in enum order. `OceanRecipe.research` (nullable) names the research that unlocks it: `RecipeLocks.install(provider)` (called by `ResearchSystem.init`) decides `lockedBy(player, recipe)`, `RecipeCrafter.craft` checks it first and returns `CraftResult.Locked(research)`, and the card shows `Requer pesquisa` (tooltip `⌀ Pesquise em /pesquisa: <nome>`) with the button disabled. With no provider installed nothing is locked.
- **Crafting**: `RecipeCrafter.craft(player, recipe)` recounts the inventory at click time and returns `CraftResult.Crafted` or `Missing(shortages)`. Consumption is all or nothing through the pure `StackAllocator` (one stack unit serves one ingredient, so plank stacks of different woods combine); the result goes to the inventory and leftovers drop at the feet; it fires `CustomCraftEvent(player, recipe.id, amount)` (battle-pass `CustomCraft` objectives listen to it). `ItemStack` cannot be built in a plain JVM test on Paper 26.3, so the tests cover `StackAllocator`, `RecipeBook` and `screen/RecipeEntries` only.
- **Screen (`screen/`)**: `RecipesScreen` opens the Textura dialog `server/plugins/Textura/configs/ui/receitas.json` through `DialogApi.openResult`. All entry maps are built by the pure `RecipeEntries` (Kotest-covered): lists `categorias` (the "Categorias" nav column, `perPage` 6: `nome`, `icone`, `descricao`, `ativa`, `acao`), `receitas` (2×2 grid of kit-style cards, `perPage` 4, each headed by the result as an 18 px `item:{item}` icon beside the bold name and the accent line `Rende {rende}`: `item`, `qtd`, `nome`, `descricao`, `rende`, `custo`, `custo_lista`, `falta`, `acao`, the status line `status` / `status_icone` / `status_estilo`, and one slot per ingredient, up to `RecipeEntries.INGREDIENT_SLOTS` = 5: `i<n>_item`, `i<n>_qtd` (the amount required), `i<n>_nome`, `i<n>_tem` (coloured "Você tem N" lore) and `i<n>_falta`, which paints that slot red through the theme's `slots.missing-art`; empty slots are hidden with `hideEmpty`) and `paginacao` (`perPage` 1; empty when there is a single page, which hides the arrows row: `pagina`, `paginas`, `sem_anterior`, `sem_proxima`). The cards (`well`) sit inside one big `sheet` panel headed by the open category (global texts `titulo` and `titulo_icone`). The craft button uses the theme look `craft` (blue, grey when disabled). Clicks: `listButton("categoria")` switches category and resets the page, `listButton("craftar")` crafts (index into the open category's full list), `button("anterior"/"proxima")` turns the page; every click redraws the dialog. Per-player state (`RecipesView`: category and page) lives in memory and is dropped on quit. The cost separator is `∙` (U+2219) because the dialog text font has no `·`. `DialogApi.openResult` decides the error path: `Shown` and `NeedsPack` (Textura already showed its "Textura necessária" fallback or told the player the pack is not ready) send nothing; `MissingScreen` and `Failed` send "A tela de receitas não está disponível." and log one `[receitas]` warning per screen id. More than `RecipeEntries.CATEGORIES_PER_PAGE` (6, the `perPage` of `categorias`) categories with recipes logs a warning once; a test keeps `RecipeCategory.entries` within it.
- **Icons and the pack**: card slots show the result as an `item:<material>` icon, which the pack only bakes if registered. `CraftSystem.init` (the first thing in `setupSystems` that touches recipes) calls `Recipes.onRegister(RecipesScreen::registerIcon)`, which replays recipes already registered and then sees every later `Recipes.register` (drift's included), so every result material reaches `DialogApi.registerItemIcons` during `onEnable`. Textura builds its pack on its own first tick at every startup, after all plugins enabled, so **a restart rebuilds the pack with the icons**. `/textura gerar` is only needed after a hot reload, or after changing `receitas.json` or recipes without a restart; until then the slot draws empty and surfaces may lack a height. `ReceitasScreenTest` in `plugins/textura` compiles the real `receitas.json` with the real kit, so a broken screen fails `:plugins:textura:localTest`.

#### Stations (`system/stations`)

The first ore source: debris clods (`torrao_areia`, `torrao_cascalho`, `torrao_lodo` in `drift.yml`, plus sand and gravel in the `barril`) are sifted into ore pieces, and pieces melt only in the custom Fundição. `StationsSystem.init(plugin)` runs after `DriftSystem`; `StationsSystem.onDisable()` must stay in `OceanBlockPlugin.onDisable()`. All recipes are `PROCESSAMENTO` and registered by `StationRecipes`; every tier above the first carries `research = <its block id>`.

- **Pieces (`item/`)**: `OrePiece` is a `CustomItem` (`pedaco_ferro` on `RAW_IRON`, `pedaco_cobre` on `RAW_COPPER`, `pedaco_ouro` on `RAW_GOLD`; `ingot` names the result). `VanillaGuard` keeps them out of vanilla: it cancels `BlockCookEvent` for a piece, sets `FurnaceStartSmeltEvent` cook time to the max so the furnace never starts, and clears `PrepareItemCraftEvent` results that use one. Station material ingredients (`StationIngredients.material`) ignore any stack carrying a custom id (`CustomIds.of`), so a piece never counts as raw iron.
- **Sieve (`sieve/`)**: `SieveBlock` is a `CustomBlock` per `SieveTier` (`peneira` 6 steps / table `madeira`, `peneira_ferro` 5 / `ferro`, `peneira_diamante` 4 / `diamante`, `peneira_automatica` 5 / `ferro`), all `COMPOSTER`, `limitPerIsland = 6`. Right click with sand, gravel or dirt (`SieveInput`) loads one; every later click advances a step (4-tick cooldown) and the last step rolls the table (`SieveRoller`, independent rolls per output) and delivers to the inventory with a `CollectNotifier` line in region `coleta`. Sneak + right click (own `LOW` `SieveListener`, the framework ignores sneak clicks) loads and steps at once. State lives in `PlacedBlock.counters` (`sieve_input`, `sieve_steps`) through the pure `SieveProgress`; the composter level shown is capped at 6 so it never reaches the bone-meal level a hopper could pull. The automatic tier ticks every 20 ticks, pulls from a container above and pushes outputs into the container or hopper below (`AutoSieve`), waiting on the last step while the target is full. The table is `server/plugins/ocean-block/peneira.yml` (`<input>.<table>` lists of `saida/min/max/chance`; `saida` is a `Material` or a piece id), copied from the bundled file when missing and parsed by `SieveTableParser` (bad rows logged under `[peneira]` and skipped).
- **Smelter (`smelter/`)**: `SmelterBlock` per `SmelterTier` (`fundicao` 200 ticks per ingot, `fundicao_melhorada` 100 ticks + 25% bonus ingot, `fundicao_funil` same plus hopper I/O), all `BLAST_FURNACE`, `limitPerIsland = 4`, ticking every 5 ticks. Right click with a piece or raw ore loads input (max 32), with fuel loads fuel (max 16; `Fuel.ticks`: planks 300, logs 1200, stick 100, coal/charcoal 1600, dried kelp block 4000); sneak + right click takes every finished ingot (max 16 stored); the vanilla inventory never opens. Ratio is 4 pieces or 1 raw ore per ingot (`SmelterRules`, pure). Everything is stored as counters under the `smelter_` prefix (`smelter_burn`, `smelter_progress`, `smelter_in/<id>`, `smelter_fuel/<mat>`, `smelter_out/<id>`), so breaking a loaded smelter keeps the load in the dropped item and placing it restores it. An `ItemDisplay` above shows what is melting (`SmelterDisplay`); idle smelters skip `markDirty`.
- **Testing**: `SieveProgress`, `SieveRoller`, `SieveTableParser` and `SmelterRules` have Kotest tests; the Bukkit side (blocks, hoppers, `VanillaGuard`) only has the manual checklist (section 10 of the acceptance plan).

#### Research (`system/research`)

Per raft team progress, paid by delivering items, timed, and counted offline. `ResearchSystem.init(plugin, paperCommandManager)` runs after `StationsSystem`; `ResearchSystem.onDisable()` must stay in `OceanBlockPlugin.onDisable()`.

- **Tree (`tree/`, `model/`)**: `ResearchTree.all` is hardcoded (8 entries: `rede`, `peneira_ferro`, `fundicao_melhorada`, `bancada_auxiliar`, `peneira_diamante`, `peneira_automatica`, `fundicao_funil`, `bancada_auxiliar_2`), each a `ResearchDefinition` with category (`COLETA`, `FUNDICAO`, `RAFT`), icon, `ResearchCost` list (key `planks` means any plank, other keys are `Material` names), duration in seconds (20 s up to 5 min), prerequisites, recipes it unlocks and `extraSlots`. The Gancho stays free; the Rede de Detritos is the first research.
- **Rules (`rules/`)**: pure `ResearchRules` (Kotest-covered): `slots` (1 + `extraSlots` of completed researches), `status`, `missing`, `deliver` (takes only what is still missing, partial deliveries add up, a fully paid research starts or queues), `startQueued` and `completeDue`, which chains finished and queued researches by their real end times, so a server that was off finishes them on the next check. One running research per slot; the rest wait in a FIFO queue.
- **Data (`data/`)**: `ResearchManager` keeps `IslandResearch` per island (collection `island_research`, unique index on `islandUuid`) and is accessed only through `edit` / `read` under one lock; the 30 s flush writes deep copies of dirty entries through `ResearchRepository.updateAll` and clears them only after success. Deliveries `saveNow`.
- **Command and screen (`command/`, `screen/`)**: `/pesquisa` (alias `/pesquisas`, `PesquisaCommand`) opens `ResearchScreen` (`configs/ui/pesquisa.json`) for the player's own island (`IslandManager.getIslandByPlayer`); there is one research state per island and no block (the old `mesa_pesquisa` table was removed on 2026-10-21, so tables already placed in a world are plain cartography tables and the framework logs their unknown id). Entries come from the pure `ResearchEntries`: `categorias`, `fila`, `pesquisas` (2×2 grid of cards like the recipe ones, 4 per page: `icone` at 18 px, the small `rotulo` ("Leva 20s") over the name, one slot per cost up to `COST_SLOTS` = 4 (`c<n>_item`, `c<n>_qtd` = what is still missing, `c<n>_tem`, `c<n>_falta` paints it red), the coloured `status` / `status_estilo` line and the `{botao}` button bound to `entregar`), `paginacao`, plus `vagas`. `ResearchEntries.costIcons()` and the tree icons are registered with `DialogApi.registerItemIcons`. `entregar` counts the inventory (ignoring custom items), calls `deliver` inside `edit` and removes exactly what was taken. `ResearchTimer` runs `completeDue` every 20 ticks for islands with running research, and `ResearchNotifier` announces each finished research in region `avisos` to the island's online players. `RecipeLocks` resolves through `ResearchLocks.reason(recipe, completed)`; a player without an island sees every researched recipe locked. `PesquisaScreenTest` in `plugins/textura` compiles the real `pesquisa.json`.

#### Progression systems (`system/battle-pass`, `system/collections`)

Two separate progression tracks, both Manager+Repository backed. The `skills` system was removed from OceanBlock on 2026-10-18 (its Mongo collection `skills` is left untouched and unused):

- **`battle-pass`** — `Challenges` is a **hardcoded enum** (display name, icon `ItemStack`, `xpReward`, and a sealed `ChallengeObjective` such as `BreakOneBlock`, `CustomCraft`, `SellValue`; `BreakOneBlock` is inert, with no progress, until subproject 5), not YAML. Adding a challenge means adding an enum entry plus the matching branch in `ChallengeListener`. `BattlePassSystem` exposes its `ChallengeListener` as a public `lateinit` so other systems can report progress into it.
- It and `collections` render their menus with Textura fonts/glyphs — see the Textura section for `TitleApi`.

`MultiTool` used to live in the plugin module and is now `content/multitool/MultiToolItem` in `custom-items`, registered like any other built-in; `/multitool` still hands it out, and `/citem give multitool` works too.

The **plugin module holds no feature code** — only `OceanBlockPlugin`, `OceanBlockCommand` and `MobControlListener`. Anything else that lands there is misplaced.

### Dependency direction (important)

Systems depend `compileOnly` on `lib:*` and occasionally on other systems; the **plugin module** depends on all of them to shade. **Systems must never depend on the plugin module** — that inverts the graph. Cross-cutting code that a low-level system would need must live in a `lib:*` module or be passed in via `init`, not reached back up into `plugins/oceanblock/plugin`.

### Shared libraries (`lib/`)

- **`instance`** — two global handles set in `onEnable`: `Instance` (`JavaPlugin`, backed by `PluginInstance`) for the Bukkit scheduler / `NamespacedKey` / logging, and `ScheduledExecutor` (single-thread `ScheduledExecutorService`, backed by `ScheduledExecutorInstance`) for off-main-thread periodic work such as repository flushes. Never touch the Bukkit API from `ScheduledExecutor`.
- **`connection`** — data layer (MongoDB), with the env-split source sets described above. Exposes a single lazy `Mongo: MongoDatabase` (database `ocean-block`) configured with an automatic POJO codec provider, so domain classes persist without hand-written codecs.
- **`coordinate`** — `SimpleLocation` and world-coordinate helpers.
- **`actionbar`** — the single owner of the action bar. **Never call `player.sendActionBar` directly** from a system: whoever writes last wins and short messages get erased by periodic ones. Publish with `ActionBar.send(player, Channel.X, component, durationTicks)`; a 2-tick render task shows the highest-`priority` live channel and re-sends every 20 ticks so it doesn't fade. Add a `Channel` enum entry per system that writes there (`FlyTimer` 0, `Combat` 10, `Drift` 15 are declared but unused today). Safe to call off the main thread.
- **`rewards`** — shared reward model (`Reward(type, value, material, amount)`, `RewardType.Message | Item | Command`) and `RewardGranter.grant(rewards, player(s))`, which handles full inventories (drops leftovers) and `%player%` / `{player}` substitution in commands. Island phases pay through it — new reward-granting features reuse it instead of re-implementing delivery.
- **`toast`** — advancement-toast popups, sent as raw `WrapperPlayServerUpdateAdvancements` packets through packetevents (grant then revoke 5 ticks later). Only `ToastApi.send(...)` is public; `ToastService` is `internal`. Add a `ToastType` entry per use case — the enum maps to the advancement frame.
- **`formatter`**, **`translation`**, **`item-builder`** (`Items` / `ItemStackExt`) — text, i18n, item construction.

### GUIs and text

- GUIs use **inventory-framework** (`me.devnatan.inventoryframework`): views are registered with `viewFrame.with(...)` and the frame is created once in `OceanBlockPlugin`.
- Text uses **Adventure MiniMessage**. Use `ocean_block.libs.formatter.Mini.mm` (or `Mini.deserialize(...)`), **not** `MiniMessage.miniMessage()` — `Mini.mm` is the shared instance carrying Textura's `<glyph:id>` / `<shift:n>` tags, which the default instance would emit as literal text. Remember `.decoration(TextDecoration.ITALIC, false)` on item display names.
- Item behavior uses **Paper data components** (`io.papermc.paper.datacomponent.*`, e.g. `CAN_BREAK`, `TOOL`, `RegistrySet`/`RegistryKey`). Verify exact builder signatures against the paper-api jar rather than guessing — the API churns between versions.

### Persistence pattern (Manager + Repository)

Stateful systems follow the same shape — read `islands` for a full example:

- `class XRepository` — owns one `Mongo.getCollection<X>("...")`, creates its unique index in `init`, and exposes `toList()` / `update(x)` / `updateAll(list)` (bulk `ReplaceOneModel` with `upsert`) / `remove(uuid)`. No business logic.
- `object XManager` — the single source of truth at runtime. `onInit()` loads the whole collection into in-memory maps; mutations touch the maps and mark ids in a `dirtyIds` set; a `ScheduledExecutor.scheduleAtFixedRate` job flushes only the dirty entries (islands: every 30s) via `updateAll`. Lookups go through the manager's maps, never through a fresh query.
- Managers with unsaved state expose `onDisable()` and **must be called explicitly** from `OceanBlockPlugin.onDisable()` — nothing wires this automatically, so a new stateful manager that isn't added there silently loses its last flush window. Every manager that buffers writes is listed there today; if you add one, add it there in the same commit. `battle-pass` (`ProgressManager`, `BattlePassManager`) is the exception that needs nothing: it writes through to Mongo on every mutation instead of buffering.
- The Kotlin `DataClassCodec` (bson-kotlin 5.1) **ignores constructor defaults**: a field missing from an old document decodes as `null` and a non-null parameter throws, failing the whole `toList()`. Adding a non-null field to a persisted data class needs a backfill in the repository `init` (`PlacedBlockRepository` sets `counters` with `updateMany(Filters.exists(..., false), Updates.set(...))`).
- A dirty-set flush must **clear the set only after the write succeeds**, and go through the repository's bulk `updateAll`/`saveAll` rather than one `update` per entry. Clearing first turns any Mongo hiccup into silent data loss — `IslandManager` had that bug.

#### Storing `ItemStack`s

`ItemStack` is not POJO-codec-friendly — **persist it as a Base64 `String`**, never as a nested object. `ItemSerializer` (`lib/item-builder`, `ocean_block.libs.item_builder`) wraps `BukkitObjectOutputStream` + Base64 for this; the auction house is the reference usage (`Auction` holds the item as `String`). Serialize at the model boundary (when the item enters/leaves the stored object), not inside repository read/write.
- `XxxSystem.init` calls `XManager.onInit()`. Systems that need a fully loaded world (e.g. `IslandsSystem`) defer it with `runTaskLater`.

### Textura plugin (`plugins/textura`)

Separate jar, hard `depend` of ocean-block, own `plugin.yml` via `plugin-yml`. It builds and serves the server resource pack at runtime using **team.unnamed `creative`**:

Source packages: `pack/` (pack assembly), `registry/` + `model/` (config parsing), `api/` (the only surface other plugins touch), `text/` (`TextMetrics`, pixel width + spacing components), `glyph/`, `http/`, `hud/`, `block/`, `menu/`, `command/`, `listener/`, `dialog/`. There is no `util/` — new code goes in the package that owns the concern.

- Registries (`GlyphRegistry`, `FontRegistry`, `TitleFontRegistry`, `ItemRegistry`, `BlockRegistry`) load YAML from `server/plugins/Textura/configs/{glyphs,fonts,items,blocks}` — mutable, so `/textura reload` re-reads them in place. `BlockRegistry` additionally indexes `OVERRIDE`-type entries by target block. Config ymls are **flat** inside each folder, named `<domain>[-<sub>].yml`; the registries recurse but subfolders only create a second way to do the same thing.
- `ResourcePackBuilder` orchestrates and delegates per domain to `FontPackWriter` / `ItemPackWriter` / `BlockPackWriter`; `PackBuilder` is the only class that talks to the creative API, and `PackAssets` maps a declared `caminho` to a file on disk plus its position in the zip. The zip is assembled **asynchronously** (guarded by an `AtomicBoolean`) into `generated/resourcepack.zip`; `PackHash.calculateSHA1` produces the hash. Either a local `ResourcePackServer` (Ktor-less mini HTTP server on `host.porta`, default 8080) serves it, or it is uploaded to LobFile when `host.lobfile.enabled` is set — the two paths are exclusive and both end by setting `packUrl` + hash. The LobFile key lives in `host.lobfile.api-key`; `TEXTURA_LOBFILE_API_KEY` overrides it when set.
- The data folder splits by lifetime: `configs/` (definitions) and `resource/` (assets, laid out exactly as the pack — the file's location *is* its key) are versioned; `data/` holds runtime state that must survive (`block-allocations.yml` — losing it changes the appearance of blocks already placed in the world); `generated/` and `external/` are gitignored. `server/plugins/Textura/README.md` documents every yml format and the reload/gerar flow — read it before touching a config.
- Other plugins consume it only through the `api/` objects (`GlyphApi`, `HudApi`, `ItemApi`, `BlockApi`, `TitleApi`/`TitleBuilder`, `TexturaTags`), which hold a `@Volatile` reference to the live registry so reloads propagate. Do not reach into `registry/` from outside.
- **The public API never exposes Kotlin types; both plugins shade their own Kotlin.** ocean-block and textura each carry a `kotlin.*` stdlib in their own plugin classloader, so any `kotlin.*` class in a public signature of `api/` or `hud/` (`Function0/1/2`, `Unit` as a type argument, `DefaultConstructorMarker`, an enum's `EnumEntries`, a companion's synthetic constructor) throws `LinkageError: loader constraint violation` the first time ocean-block calls it. Use Java functional types (`Supplier`, `IntSupplier`, `BooleanSupplier`, `Consumer`, `IntConsumer`) or Textura `fun interface`s (`DialogBindsConfig`, `DialogButtonAction`, `DialogListAction`); no default parameter values on public functions or constructors (write overloads or secondary constructors; a data class's generated `copy$default` is the one allowed exception); no companion objects on public API classes; enums that cross the boundary are Java enums in `src/main/java` (`DialogOpenResult`, `HudSide`). `PublicApiKotlinTypesTest` reflects over every public class of `api/` and `hud/` (plus `TitleFontSource`) and fails on any of this.
- `TitleApi` positions text by pixel inside GUI titles: each `y` becomes a generated `minecraft:font-ui-<y>` font in the pack. **A new `y` only exists after `/textura gerar`**, so register ascents early (`TitleApi.registerAscent(...)`, at system `init`) rather than the first time the menu opens. `TitleApi.source(path, baseAscent)` points a title at a custom font JSON (e.g. the digit-only `oneblock_level` font) so the `y` still means effective ascent.
- `TexturaTags` defines `<glyph:id>`, `<glyph:id:font>` and `<shift:n>`; both are self-closing and **never throw** — an unknown id renders empty rather than breaking the whole title. `Mini.mm` in `lib:formatter` is the MiniMessage instance carrying these resolvers.
- `dialog/` draws screens inside the vanilla dialog (design: `docs/superpowers/specs/2026-10-12-dialog-ui-json-design.md`): screens in `configs/ui/<id>.json`, themes in `configs/ui/*.yml`, art in `resource/assets/oneblock/textures/ui/`. `/textura gerar` writes the `oneblock:ui/*` fonts and publishes the `UiKit`; surfaces are pre-rendered per height (width is free at runtime) and sized icons per size, so changing a panel height or icon size needs a regenerate. Clicks travel as `ClickEvent.custom(textura:ui, "<token>:<index>")` handled by `DialogOpener` (no per-render callbacks). Other plugins open screens only through `DialogApi.open(player, id) { binds -> binds.switch(...); binds.text(...); binds.button(key) { click -> } }` (Boolean) or `DialogApi.openResult(...)`, which returns `DialogOpenResult.Shown | NeedsPack | MissingScreen | Failed` (`NeedsPack`: Textura already showed its pack fallback or told the player; callers should only report `MissingScreen`/`Failed`). Repeated content: any node takes `"repeat": "<list>"` plus optional `"perPage": N` (max 64), fed by `list(key, Supplier<List<Map<String, String>>>)`, paged by `listPage(key, IntSupplier)`; a repeated `button`/`nav` with `bind` calls `listButton(bind, DialogListAction { click, index -> })` with the index in the full list. Slot `item`/`count`/`name`/`lore`, icons and flags take `{field}` from the entry. `/textura gerar` pre-renders every list-count combination (up to 512) and only bakes `item:` icons that code registered with `DialogApi.registerItemIcons(materials)` before the build. An `item:<name>` icon reads the vanilla client jar at `item/<name>`, then `block/<name>`, `_front`, `_side`, `_top` (`VanillaTextures`), so block items such as `loom` resolve. `BlockIcon` / `VanillaTextures.faces` can draw a block item as an isometric cube instead, but it is not wired in (the user preferred the flat face for now). Each click consumes its render token before the action runs, so a queued second click on the same render does nothing; the redraw issues new tokens. Multi-line tooltips are coloured per line after placeholders resolve (`∙` highlight, final `✔` green, `⌀`/`✖` red; see the README). Screens also accept the Studio editor's keys (pages + `nav`, `onClick` actions `[open] [page] [set] [message] [console] [player] [sound]`, `dropdown`, `slider`, icon `states`, `{key?a:A|b:B}` / `%papi%` placeholders); control values are strings persisted per player in PDC (`textura:ui_<bind>`) unless code binds them, readable via `DialogApi.setting(player, key)`.

### Textura Studio (`tools/textura-studio`)

Local editor for the dialog screens, modelled on the resourcepack.ai Studio (spec: `docs/superpowers/specs/2026-10-19-textura-studio-base-design.md`). `./gradlew :tools:textura-studio:run` builds the React frontend in `web/` (npm) and serves everything on `http://127.0.0.1:7070` (`TEXTURA_DATA` overrides the data folder, `-Dstudio.port` the port). The Kotlin backend reuses Textura's own `ScreenParser` → `ScreenCompiler` → `UiLayout` offline and paints the `LaidOut` with Java2D into a monitor-sized PNG (same slicing as `UiPackWriter`, fonts from `configs/fonts/custom.json`, vanilla dialog frame from the client jar in `generated/vanilla/`), so the preview matches the game. Saving writes `configs/ui/<id>.json` directly; the player still runs `/textura reload`. It never writes anything else in the server folder (glyph ymls are read with `YamlConfiguration`, not `GlyphRegistry`, which would rewrite them). `OfflineRegistryAccess` (registered via `META-INF/services`) exists only so `org.bukkit.Material` can initialise outside a server. Repeated lists preview with `perPage` empty entries (`{field}` shows literally) unless the editor sends sample entries (`lists`/`values` in `POST /api/preview`). Visual editing relies on an engine hook: `ScreenCompiler` tags every compiled `UiNode` with its `DefNode.path` and `UiLayout` returns a `PlacedBox(tag, x, y, w, h)` per tagged node in `LaidOut.boxes` (repeated instances get `path[index]`); the game ignores both. The frontend recomputes the same path labels (`name` or `<shape>#<index>`, joined by ` > `, page id as the first segment for page documents) in `web/src/editor/tree.ts` — keep the two in sync if the parser ever changes how it names nodes. Besides dialogs the Studio edits notification regions (`#/notificacoes`, preview in `render/HudPreview.kt` mirrors `LineGeometry` + `text.vsh` — the notify classes are `internal` to Textura, so the geometry is duplicated there and must follow any change to them), tests the HUD bossbar (`#/hud`), and edits glyphs (`#/glyphs`) and themes (`#/temas`). `StudioFiles` is the only writer: a path whitelist (`configs/{hud,glyphs,ui}/*.yml`, `resource/assets/**.png` and `.png.slice`) that keeps `config.yml` (LobFile key) unreachable.

## Conventions

- **Do not write comments in code.** No KDoc, no inline notes, no "why" blocks — not in Kotlin, not in Gradle scripts, not in YAML you generate. Name things well and let the code stand alone. This overrides any habit of explaining reasoning in-file: put the explanation in the chat response instead. Only exception: a comment the user explicitly asks for, or one that already exists and you are editing around.
- User-facing strings are in **Portuguese**; keep that when editing nearby code. Pre-existing comments are also in Portuguese — leave them as they are, don't translate or extend them.
- Commits follow `type(scope): description` (`feat`, `fix`, `refactor`, `docs`, `chore`) — see `git log`.
