# CLAUDE.md

OceanBlock is a fork of one-block; its design lives in `docs/superpowers/specs/2026-10-18-oceanblock-design.md`. Rename rule: Kotlin packages are `ocean_block.*`, but Textura keeps `one_block.textura` (and every `one_block.textura.*` import) and the literals `"oneblock"`, `oneblock:gui`, `oneblock.admin` and `oneblock_level` are preserved.

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

This is a Gradle multi-module monorepo (Kotlin/JVM 2.3.0, JDK 25 toolchain, Paper 26.3). The shippable artifact is the `ocean-block` Paper plugin, assembled by shading many internal modules into one jar.

**Primary build+deploy command** (builds the shaded jar and copies it into `server/plugins/`):

```bash
./gradlew :plugins:oceanblock:plugin:localDeploy
```

- `localJar` / `localDeploy` come from the `paper-plugin` convention. `productionJar` builds the prod jar into `build/libs` only.
- The dev server (Paper) must be **stopped** before deploying — Windows locks the running jar and the copy fails. `localDeploy` intentionally does not track state (its destination `server/plugins/` holds other plugins' runtime data, e.g. LuckPerms' H2 DB).
- After deploying, the server must be **restarted** (or the plugin reloaded) to pick up the new jar.

### Docker (dev server + Textura Studio)

`docker-compose.yml` at the repo root runs both, controlled from Docker Desktop or the CLI:

- **`servidor`** (`oceanblock-servidor`): the stock `eclipse-temurin:25-jre` image running `paper.jar` with the same JVM flags as `server/start.bat`, the repo's `server/` bind-mounted at `/server` (worlds, plugins and configs stay in the working tree, so `localDeploy`, git and the Studio see the same files), port `25566`, `TZ=America/Sao_Paulo`. MongoDB stays the Windows service: the container reaches it through `host.docker.internal` (`OCEANBLOCK_MONGO_URI`, read by `lib/connection/src/local`; unset means `mongodb://localhost:27017/`, so `start.bat` still works). `restart: on-failure`, so `/stop` stays stopped; `docker compose stop servidor` sends SIGTERM and Paper saves the worlds (grace period 90 s).
- **`studio`** (`oceanblock-studio`): image built from `tools/textura-studio/Dockerfile`, which only copies the prebuilt `build/install/textura-studio/lib` and `web/dist` (build them on the host first). It binds `0.0.0.0` inside the container (`STUDIO_BIND`) but is published only on `127.0.0.1:7070`, and `server/plugins/Textura` is mounted at `/data`.
- **Ask the user before stopping or restarting the server** (any `docker compose stop/start/restart servidor`, including to install a jar), and wait for a yes. Building, testing and committing need no permission; only taking the server down does. Another session asking for a restart is not the user's yes.
- Install a new jar: `docker compose stop servidor`, then `./gradlew :plugins:oceanblock:plugin:localDeploy :plugins:textura:localDeploy`, then `docker compose start servidor`. Console: `docker attach oceanblock-servidor` (detach with Ctrl-P Ctrl-Q, never Ctrl-C). Logs: `docker logs -f oceanblock-servidor`.
- Rebuild the Studio after changing it: `./gradlew :tools:textura-studio:installDist :tools:textura-studio:webBuild`, then `docker compose up -d --build studio`.
- Never run `start.bat` or `:tools:textura-studio:run` while the containers are up: two servers on the same `server/` folder corrupt the worlds, and the Studio port is taken.

### The `isLocal` mechanism — read before running any Gradle task

The build mode is derived from whether **any requested task name contains the substring `local`** (case-insensitive), via `gradle.startParameter.taskNames`. This flag (`isLocal`) changes dependencies and source sets in `plugins/oceanblock/plugin` and `lib/connection`:

| | local mode (task name has "local") | production mode (anything else) |
|---|---|---|
| `com.redescreen:sdk:1.0` | skipped | required (**only exists in the prod environment**) |
| MongoDB driver | `implementation` (shaded) | `compileOnly` |
| `lib:connection` source | `src/local/kotlin` | `src/production/kotlin` |

`lib:connection` additionally accepts `-Penv=local` as an override, so `./gradlew :lib:connection:build -Penv=local` works; the plugin module honors task names only.

Consequence: a plain `./gradlew build`, `test`, or `:some:module:compileKotlin` runs in **production mode** and fails resolving `com.redescreen:sdk:1.0`. Always drive local work through a `local*` task. To compile everything locally, `:plugins:oceanblock:plugin:localDeploy` transitively builds all modules.

### Local dependency jars (not on any repo)

Three paths are wired as file dependencies and must exist on disk or the build fails with unresolved symbols rather than a dependency error:

- `jars/inventory-framework-paper-3.7.1.jar` — inventory-framework, `compileOnly` for every module via `paper-common`, `implementation` (shaded) in both plugin modules. The version catalog entry `inventoryFramework` is unused.
- `jars/ModelEngine-4.1.0.jar` — ModelEngine (`com.ticxo.modelengine.api`). It was used only by the removed `system/spawn` module (NPC models); nothing compiles against it today.
- `.dep/` — a `fileTree` of server-only APIs (currently `SkinsRestorer.jar`), consumed `compileOnly` by `system/islands`.

`jars/packetevents-spigot-2.13.0.jar` is **not** one of them — packetevents resolves from Maven (`repo.codemc.io`) via the `packetevents-spigot` catalog entry. That jar is just the copy you drop into `server/plugins/`; it is a runtime `softDepend`, so the build succeeds without the server plugin but `lib:toast` silently no-ops (logs once) if PacketEvents is missing at runtime.

### Tests

Tests use **Kotest 5.9 on the JUnit 5 platform**. `paper-common` does *not* wire testing — a module that wants tests must add `testImplementation(libs.kotest.runner)` + `libs.kotest.assertions` (plus `libs.paperApi` when the code under test touches Bukkit types) and `tasks.test { useJUnitPlatform() }` to its own `build.gradle.kts`. Only `plugins/textura`, `system/custom-items`, `system/islands`, `system/drift`, `system/craft`, `system/machines`, `system/preferences`, `system/level`, `system/missions`, `system/scoreboard` and `system/sell` have tests today; `system/level` and `system/missions` depend on `lib:connection`, so they also have a `localTest` alias. Tests live under `src/test/kotlin`.

```bash
./gradlew :plugins:oceanblock:system:custom-items:test
./gradlew :plugins:textura:localTest
./gradlew :plugins:textura:test --tests "*CooldownStore*"
```

`plugins/textura` also registers a `localTest` alias whose only purpose is to put `local` in the task name so the build resolves in local mode. Modules that do **not** depend on `lib:connection` test cleanly. A whole-project `test` fails in production mode on the `com.redescreen:sdk` resolution unless that SDK is present.

## Architecture

### Convention plugins (`build-logic/`)

- **`paper-common`** — base for every module: Kotlin + Shadow, paper-api (`26.3.build.192-stable`, Adventure 5 — `ClickEvent<T>` is generic and `net.kyori.examination` is gone, so Textura shades and relocates it for `creative`) and the local inventory-framework jar as `compileOnly`, Aikar ACF (`co.aikar:acf-paper`) as `implementation`, JDK 25, Shadow 9.2.2 (9.3+ needs a newer Gradle; 8.x cannot read Java 25 classes), and the full list of third-party Maven repos. Every module (including `lib:*` and `system:*`) produces a shadowJar with an empty archive classifier.
- **`paper-plugin`** — applies `paper-common` + `plugin-yml.bukkit`, disables the thin `jar` task (it would collide with shadowJar on the same output name), and adds `localJar` / `productionJar` / `localDeploy`. Only the two real plugins apply it. Because the thin `jar` is disabled, the convention also republishes `shadowJar` into `apiElements`/`runtimeElements`: without that, a project that applies `paper-plugin` has **no consumable artifact**, and `compileOnly(projects.plugins.textura)` in `lib:formatter` resolves to nothing — it only compiles while a stale jar happens to sit in `build/libs`, and fails on any clean build.

### Two shippable plugins vs. shaded modules

Only `:plugins:oceanblock:plugin` and `:plugins:textura` are standalone plugin jars. **All `:lib:*` and `:plugins:oceanblock:system:*` modules are shaded into the ocean-block jar** — the plugin module `implementation`s every `:plugins:oceanblock:system:*` and `:lib:*` and merges them at `shadowJar` time. `textura` is a separate jar declared in ocean-block's `depend` list (`PlaceholderAPI`, `SkinsRestorer`, `Textura`), not shaded — systems that need it (e.g. `islands`) take `compileOnly(projects.plugins.textura)` and resolve it at runtime from the server.

### System module pattern

Each feature lives in its own module under `plugins/oceanblock/system/<name>/` and exposes a singleton `object <Name>System` with an `init(...)` function. `OceanBlockPlugin.onEnable()` wires everything in three phases:

- `setupSystems()` — calls every `XxxSystem.init(plugin, viewFrame | paperCommandManager)`.
- `setupCommands()` — registers Aikar ACF commands via `PaperCommandManager` (`@CommandAlias`, `@Subcommand`, `@Default`, `@CommandPermission`).
- `setupListeners()` — registers Bukkit `Listener`s.

To add a feature module: register it in `settings.gradle.kts`, add it to the plugin's dependency loop (systems under `:plugins:oceanblock:system:` are auto-included), and call its `init` in `setupSystems()`. Those two steps are independent — a module can be included and shaded without being `init`ed. Check `setupSystems()` before assuming a module under `system/` is live.

Systems may `compileOnly` on other systems to register into them (e.g. `drift` depends on `custom-items` and calls `CustomItemRegistry.register(GanchoItem)` from its own `init`, and on `islands` for island lookups). Keep that registration inside the depending system's `init`, not in the plugin module.

#### Custom-item framework (`system/custom-items`)

Reusable in-game item behavior lives here — do **not** hand-roll per-item click listeners in other modules. Define a behavior by subclassing `CustomItem` (`api/CustomItem.kt`): override the appearance fields (`id`, `material`, `displayName`, `lore`, `itemModel`, `cooldownMillis`, `heldTickInterval`) and the hooks you need (`onRightClick`, `onLeftClick`, `onInteractEntity`, `onConsume`, `onHeldTick`; plus optional `listeners()` / `tasks()`). `build()` stamps the `id` into item NBT under `CustomItemKeys.ID`; `CustomItemRegistry.fromItemStack(...)` resolves an `ItemStack` back to its `CustomItem` by that tag. Register built-ins in `CustomItemSystem.registerBuiltInItems()` (e.g. `MultiToolItem`). The three paxels (`PaxelItem`, `iron_paxel`, `diamond_paxel`, `netherite_paxel`) are the only OceanBlock items with a vanilla crafting-table recipe (the user asked on 2026-10-25): `PaxelRecipes` registers one `ShapedRecipe` each (key `ocean-block:paxel_<id>`, pure `PaxelRecipeRules`, Kotest-covered): axe, pickaxe and shovel of the tier across the top row and two sticks down the middle column, any durability. Its `PrepareItemCraftEvent` listener clears the result when any matrix item is a `CustomItem` (a Picareta fundidora or a paxel is also an iron/diamond pickaxe underneath). A single global tick task in `CustomItemSystem` drives every item's `onHeldTick` at its own `heldTickInterval`; a shared `CooldownStore` gates activations. Custom blocks whose `material` is `BARRIER` are furniture (a display entity draws them): `FurnitureBreakListener` lets survival players break them with 3 left clicks within 30 ticks (pure `FurnitureHits`), with particles and sounds from `CustomBlock.furnitureFeel` (default `IRON_BLOCK`), then fires a synthetic `BlockBreakEvent` so `CustomBlockListener` does the access check and the stateful drop. `BlockItemUpgradeListener` rebuilds, on join and on inventory open, any custom block item whose material is no longer the block's `material` (pure `BlockItemRules`), keeping its stored state.

#### Starting island (`system/islands`)

The player starts on an island pasted from a schematic, not a raft. `StarterIsland.generate` (called by `IslandManager.createIsland` and `IslandResetService.resetTerrain`) pastes `server/plugins/ocean-block/templates/island.schem` (tracked in git) asynchronously through FAWE with `ignoreAirBlocks(true)`, clipboard origin at `(lot center X, IslandPlacement.PASTE_Y = 64, lot center Z)`. The schematic was copied standing at Y 64 on the island center. Its bounding box is 18×25×16 (offset -8, -13, -7), but the solid island is only about 11×11 (X/Z -4..+6 from the center) and spans Y 54–75, with the ground at Y 63. `IslandPlacement.center` is Y 63 (`GROUND_Y`) and `IslandPlacement.spawn` is the center block + 0.5 at Y 64. A missing schematic or a failed paste logs `[ilha]` at severe and places the main-thread fallback: 3×3 `GRASS_BLOCK` at Y 63 over `DIRT` at Y 62. `generate(island, onReady)` (and `IslandManager.createIsland(player, onReady)`) invoke `onReady` on the main thread once the paste completes or the fallback is placed (immediately if the world is not loaded; synchronously when the schematic is missing). Anything that teleports a player onto a fresh or reset island must do it inside `onReady`, never right after the call: the `/ilha` default command, the first-join auto-create in `PlayerListener` and `resetTerrain` all do. There is no spawn system any more (the `system/spawn` module, with `/spawn`, `/setspawn`, `/build`, NPCs, holograms and the island portal, was removed on 2026-10-26); the `spawn` world is still created by `system/worlds` (`worlds.yml`, `type: Void`) but nothing sends players there. `PlayerListener` puts every login outside the island world on the player's home island (`IslandManager.getHomeIsland`, the pure `MemberRules.homeIsland`: the owned island, else the first island where the player is a member) and every respawn that is not a bed or anchor respawn there too. Every teleport onto the island targets `spawn + (0, 2, 0)`; `spawn` already holds the +0.5 block center. Player-facing text says "ilha" (feminine: "sua ilha"); the command is `/ilha` (aliases `island`, `is`). There is no island HUD any more (the old `IslandHud` bossbar and `SpawnHudListener` were removed on 2026-10-19); on-screen feedback goes through Textura notifications.

**Cobblestone generator (`generator/`)**: `GeneratorListener` handles `BlockFormEvent` inside an island lot: when lava and water would form `COBBLESTONE` or `STONE`, the block is replaced by a weighted roll for the island's `IslandUpgrade.Generator` level (0–4, bought in the `/ilha` upgrades menu: 25k, 100k, 400k, 1.5M coins). The table is `server/plugins/ocean-block/gerador.yml` (`niveis.<n>.<BLOCK>: weight`), copied from the bundled file when missing and parsed by the pure `GeneratorTableParser` (invalid levels, unknown blocks and non-positive weights are logged under `[gerador]` and skipped; a level without its own table uses the highest one below it; no valid level means plain cobblestone). `GeneratorRoller` does the cumulative weighted pick. Default (the user's order of 2026-10-25): level 0 cobblestone, stone, coal, copper and iron; level 1 adds lapis and redstone; level 2 gold and emerald; level 3 diamond; level 4 adds nothing new and only raises the ore weights (diamond 3 to 6 of 100). The server copy in `server/plugins/ocean-block/gerador.yml` is not overwritten by a new bundled table, so a table change must also be copied there. The file is read once at startup. For progression, `GeneratorListener` also marks every formed position in the in-memory `GeneratorBlocks` (`BlockKey` world+x+y+z, pure `GeneratorBlockSet`, Kotest-covered) and fires `GeneratorFormedEvent(island)`; `GeneratorBreakListener` turns a `BlockBreakEvent` (MONITOR, ignoreCancelled) on a marked position into `GeneratorBlockBrokenEvent(player, material)` and a `BlockPlaceEvent` there clears the mark, so placing and breaking stone never counts and the Minerador (which breaks with `setType`) never fires it. Marks are lost on restart. `UpgradeView` fires `IslandUpgradeEvent(island, upgrade, level)` after a purchase.

**Island dialog (`dialog/`)**: `/ilha` with no argument creates the island when the player has none, otherwise opens the Textura dialog `configs/ui/ilha.json` (theme `abismo`, styled after a single dark frame with a thin light border, caps-only bitmap fonts in `configs/fonts/`: `pequena`, an own 5×5 wide caps design at 2/3 GUI px per texel so it is crisp at GUI scale 3, and `titulo` / `cabecalho`, rasterized from the Minecraft Ten TTF (KendroType, freeware non-commercial, a commercial licence is needed for a monetized server) at 4/3 and 2/3 GUI px per texel; accents are drawn over the base letter because the TTF has none; no text shadow) through `IslandDialog.open`; `/ilha menu` still opens the chest hub, and the dialog falls back to it on `MissingScreen`/`Failed`. The left stage shows the player as a still three-quarter bust (head and shoulders seen from the front-right and a little above): `PlayerSkins` downloads the profile skin asynchronously (cached by URL, `DefaultSkin` when missing or failing) and the pure `PlayerFigure.bust` ray-traces the skin boxes (overlay layers, slim arms, legacy 64×32) into a 70×100 image drawn by the Textura `pixels` node at scale 2. The skin waits at most 4 s before the dialog opens without the figure. Buttons close the dialog and open the existing chest menus (members, upgrades, settings, visits) or run `nivel`, `missoes`, `receitas`.

**Island menu (`view/`, `member/`)**: the chest hub `IslandView` (`/ilha menu`); `/ilha ir` (alias `home`) teleports, `/ilha menu` also opens the hub, `/ilha <dono>` goes to an island where the player is owner, member or trusted. The hub (and every sub-menu) takes the `Island` as the view's initial state; `IslandMembership.menuIsland` picks it through the pure `MemberRules.menuIsland`: the island the player stands on if they own it or are a member, else their own. The hub links to `MembersView`, `UpgradeView`, `SettingsView`, `VisitsView` and runs `receitas` / `nivel` / `missoes` with `performCommand` (islands does not depend on craft, level or missions). `PlayerPickerView` lists online players for `PlayerPick.Mode.Invite` or `Block`. Members are added only by invite: `IslandMembership.invite` (menu or `/ilha convidar`, alias `member`) stores a 60 s invite in the in-memory `IslandInvites` and sends a clickable `[ACEITAR]` (`/ilha aceitar [dono]`); invites are dropped on quit and never persisted. `MemberRules.checkInvite` / `checkAccept` (owner only, not self, not already a member, not blocked, `members.size < Island.maxMembers()`, which is `(Members level + 1) * 3`) are Kotest-covered. Only the owner removes members, blocks, unblocks and toggles public; blacklist checks go through `Island.isBlocked` (names are stored lowercase). The island menus are plain vanilla chests with no background art (the user asked for the default look on 2026-10-23): `menuTitle(title)` in `ViewItems.kt` is a dark-gray text title, navigation uses real `ARROW` items (`backItem`, `navItem`), and `UpgradeView` lists every `IslandUpgrade` as a textured head in row 2 (level, next price, click to buy). The phase views stay registered but nothing in the hub opens them.

#### Drift and hook (`system/drift`)

Debris floats past each active island and the player pulls it in for materials. `DriftSystem.init(plugin, viewFrame)` runs after `IslandsSystem` and `CustomItemSystem`, and `DriftSystem.onDisable()` must stay in `OceanBlockPlugin.onDisable()`: it cancels the tasks and removes every tracked display.

- **Config (`config/`)**: `DriftFile.load` copies the bundled `drift.yml` to `server/plugins/ocean-block/drift.yml` when missing and hands it to `DriftConfigParser`, which clamps bad numbers to a default (with a warning) and skips invalid types/drops/materials (logged, never fatal). No valid type means a `severe` log and drift off; the rest of the plugin keeps working. Keys: `corrente` (`direcao` EAST/WEST/SOUTH/NORTH, `velocidade`, `comprimento`, `largura`, `largura-minima`, `altura`, `riscos`, `riscos-por-segundo`), `spawn` (`intervalo-ticks`, `maximo-por-lote`, `tempo-preso-segundos`), `animacao` (`balanco`, `periodo-balanco-ticks`, `inclinacao-graus`, `giro-graus-por-segundo`, `sinuosidade`, `periodo-sinuosidade-ticks`, `variacao-velocidade`, `rastro`), `obstaculo` (`profundidade-maxima`, `velocidade-mergulho`, `tempo-sumir-ticks`), `coleta` (`raio-gancho`, `raio-toque`), `rede` (`raio`), `detritos.<id>` (`peso`, `exibicao`, `escala`, optional `afundamento`, `drops` with `material/min/max/chance`). Units: `velocidade` is blocks per tick, lengths/radii/`altura` are blocks, intervals are ticks except `tempo-preso-segundos`. **`largura` and `largura-minima` are half-widths**: the lateral spawn offset (`DriftLane.lateralOffset`) has a magnitude uniform in `[largura-minima, largura]` and a random sign, so debris passes alongside the island shore on either side and never down its middle (defaults 8 and 13; the solid island reaches about 6 blocks from the center, so debris passes 2–7 blocks off the shore). `largura-minima` is clamped to `0..largura` with a warning; 0 restores the old full band `[-largura, +largura]`. The current streaks use the same offset. The config is read once in `init`; editing `drift.yml` needs a restart.
- **Lanes (`lane/`)**: `DriftLane` is pure geometry. A lot's lane is centered on the island's center block (origin + 0.5) and `comprimento` long along the current; debris spawns at the upstream end with a lateral offset and is dropped once past the downstream end.
- **Debris (`debris/`)**: `DebrisManager` owns two global `BukkitTask`s (spawn every `intervalo-ticks`, move every 2 ticks) and the list of live `Debris` (a non-persistent `ItemDisplay` with `teleportDuration = 2`). A lot is active only while an online player stands inside it (`IslandManager.getIslandAt`); the next move tick removes all debris of a lot that is inactive or no longer exists. `BlockProbe` classifies each block as **solid** (`isSolid`, via `DebrisRules.isPassable = !isSolid`; checked first, so a waterlogged slab is solid), **water** (`WATER`, `BUBBLE_COLUMN`, `KELP`, `KELP_PLANT`, `SEAGRASS`, `TALL_SEAGRASS` or waterlogged) or **air**. Depths count down from `raftY = floor(altura)` (Y 62, the sea surface; the identifier predates the island). A debris is in one of three `Support` states (pure rules in `GravityRules`, Bukkit side in `DebrisFall`):
  - **Floating** (`DebrisDive`, pure rules in `DiveRules`): it drifts at the water surface of its column (`altura - depth - afundamento + bob`, the old height with a normal sea). If the next column's block at its level is solid, it **dives**: it picks the shallowest depth up to `obstaculo.profundidade-maxima` that is water at the next position and reachable through water in its current column (never through air), sinks or rises there at `velocidade-mergulho` without advancing, travels at `floor(altura) - depth + 0.5` with 30% bob and bubbles instead of the wake, and resurfaces once the surface ahead and the column above are water. If both that block and the next column's block at its current rendered height (`floor(levelY)`, which differs mid-dive) are air, it advances and starts falling; this check keeps a rising or sinking debris from clipping into a block. If its own block stops being water, it falls. The decision order (unloaded → unsupported → drop → dive target) is the pure `DiveRules.passage`. The dive search is capped at `min(max(profundidade-maxima, depth), profundidade-maxima + 4)`. Each column is classified at most once per step, through the per-step `ColumnKinds` memo.
  - **Falling**: item gravity (`vy -= 0.04; vy *= 0.98` per tick, capped at -1 block/tick), with no horizontal advance. Entering water makes it float and rise to that column's surface. Touching a solid block lands it **on the ground** at `top + 0.25·escala`, with no bob or spin. It is removed below `world.minHeight` or more than 64 blocks below `raftY`.
  - **On the ground**: still. Support is tested at the stored landed block (`landedTopY`), not at its rendered Y. Water returning there makes it float again, and losing the block underneath makes it fall. `escala` is clamped to 0.1..2.0.
  With no dive passage it is stuck. The stuck clock clears only when the debris actually advances along the lane (or starts falling or floating again), not while it holds mid-dive. Stuck and grounded debris both run the stuck clock: after `tempo-preso-segundos` the debris fades out (sinks 0.5 block and shrinks to scale 0 over `tempo-sumir-ticks`) and is removed. Stuck, grounded and falling debris can still be touched and hooked; only fading debris cannot. **Debris never force-loads chunks**: spawning is skipped, and a drifting debris is removed, when its target chunk is not loaded (`DebrisEntities.isLoaded`).
- **Floating animation**: `Debris.point` stays the straight base point on the lane; `DebrisPose` turns it plus `ageTicks` and the per-debris `FloatParams` (phases, spin direction, speed factor, rolled at spawn) into the rendered position (lateral meander, `y = levelY + bob`, where `levelY` is the surface/dive/fall height above) and a yaw/pitch/roll `leftRotation` interpolated over 2 ticks, all from the pure sine helpers in `FloatMotion`. The stuck check and lane end use the rendered x/z; `DebrisParticles` draws the wake behind each free debris every 10 ticks and the `FISHING` current streaks per active lot (loaded chunks only).
- **Collecting (`collect/`, `hook/`)**: by touch (`raio-toque`) or by reeling in the Gancho (nearest free debris within `raio-gancho` of the hook, pulled to the player over 10 ticks). `CollectorRule` allows owner, members and trusted names only; everyone else gets nothing, not even a message. Every delivery to a player (Gancho or touch, never the net) fires `DebrisCollectedEvent(player, typeId, byHook)` from `DebrisMotion.deliver`, which `level` and `missions` listen to. `DebrisDelivery.deliver` is the single delivery path: inventory first (leftovers drop at the feet), pickup sound, splash particles, and a `CollectNotifier` notification in the Textura region `coleta` (item icon + `+N <item>`, 60 ticks, key `coleta:<MATERIAL>`; `CollectTally` sums repeated pickups of the same item while the line is alive). A net that becomes full sends `Sua Rede de Detritos ficou cheia!` with the net icon (`glyph:rede_icone`, a 16 px isometric render in `configs/glyphs/icons.yml`; every glyph is baked as a notification icon) to the island's online players in the region `avisos` (`NetFullNotifier`, once per fill, re-armed through `PlacedBlock.notifiedFull` when the net has a free slot again). `DriftSystem.init` registers the item icons of every drop material with `NotificationApi.registerItemIcons` during `onEnable`, before the startup pack build. `DropRoller` rolls each drop independently; a roll with no drops yields one `STRING`. The Gancho is a `CustomItem` (`GanchoItem`, a `FISHING_ROD`) registered in `CustomItemRegistry`, crafted only through the `craft` system (`DriftRecipes` registers it in `Recipes`, no vanilla recipe) and handed out by `FirstJoinListener` (`!hasPlayedBefore()`). `GanchoListener` only reads `PlayerFishEvent`, so vanilla fishing with it keeps working.
- **Debris net (`net/`)**: `NetBlock` is a `CustomBlock` (id `rede`, `limitPerIsland = 4`, `storageCapacity = 27`) built as furniture like the Minerador: its block is a `BARRIER` and `NetDisplay` keeps one non-persistent `ItemDisplay` (transform `NONE`, PAPER with item model `oneblock:rede`, tagged `oceanblock:rede_display`) showing an own model in the style of a reference the user gave: dark wood posts that pass the top by 1 px, wooden rails on every edge, a plank floor and four double-sided white rope nets you can see through (`resource/assets/oneblock/models/block/rede.json`, item definition `items/rede.json`, textures `textures/block/rede/rede_{poste,trave,malha}.png`). ### Dependency direction (important)

Systems depend `compileOnly` on `lib:*` and occasionally on other systems; the **plugin module** depends on all of them to shade. **Systems must never depend on the plugin module** — that inverts the graph. Cross-cutting code that a low-level system would need must live in a `lib:*` module or be passed in via `init`, not reached back up into `plugins/oceanblock/plugin`.

### Shared libraries (`lib/`)

- **`instance`** — two global handles set in `onEnable`: `Instance` (`JavaPlugin`, backed by `PluginInstance`) for the Bukkit scheduler / `NamespacedKey` / logging, and `ScheduledExecutor` (single-thread `ScheduledExecutorService`, backed by `ScheduledExecutorInstance`) for off-main-thread periodic work such as repository flushes. Never touch the Bukkit API from `ScheduledExecutor`.
- **`connection`** — data layer (MongoDB), with the env-split source sets described above. Exposes a single lazy `Mongo: MongoDatabase` (database `ocean-block`) configured with an automatic POJO codec provider, so domain classes persist without hand-written codecs.
- **`coordinate`** — `SimpleLocation` and world-coordinate helpers.
- **`actionbar`** — the single owner of the action bar. **Never call `player.sendActionBar` directly** from a system: whoever writes last wins and short messages get erased by periodic ones. Publish with `ActionBar.send(player, Channel.X, component, durationTicks)`; a 2-tick render task shows the highest-`priority` live channel and re-sends every 20 ticks so it doesn't fade. Add a `Channel` enum entry per system that writes there (`FlyTimer` 0, `Combat` 10, `Drift` 15 are declared but unused today). Safe to call off the main thread.
- **`rewards`** — shared reward model (`Reward(type, value, material, amount)`, `RewardType.Message | Item | Command`) and `RewardGranter.grant(rewards, player(s))`, which handles full inventories (drops leftovers) and `%player%` / `{player}` substitution in commands. Island phases pay through it — new reward-granting features reuse it instead of re-implementing delivery.
- **`toast`** — advancement-toast popups, sent as raw `WrapperPlayServerUpdateAdvancements` packets through packetevents (grant then revoke 5 ticks later). Only `ToastApi.send(...)` is public; `ToastService` is `internal`. Add a `ToastType` entry per use case — the enum maps to the advancement frame.
- **`formatter`**, **`translation`**, **`item-builder`** (`Items` / `ItemStackExt`) — text, i18n, item construction.

### GUIs and text

- GUIs use **inventory-framework** (`me.devnatan.inventoryframework`): views are registered with `viewFrame.with(...)` and the frame is created once in `OceanBlockPlugin`.
- Text uses **Adventure MiniMessage**. Use `ocean_block.libs.formatter.Mini.mm` (or `Mini.deserialize(...)`), **not** `MiniMessage.miniMessage()` — `Mini.mm` is the shared instance carrying Textura's `<glyph:id>` / `<shift:n>` tags, which the default instance would emit as literal text. Remember `.decoration(TextDecoration.ITALIC, false)` on item display names.

### Persistence pattern (Manager + Repository)

Stateful systems follow the same shape — read `islands` for a full example:

- `class XRepository` — owns one `Mongo.getCollection<X>("...")`, creates its unique index in `init`, and exposes `toList()` / `update(x)` / `updateAll(list)` (bulk `ReplaceOneModel` with `upsert`) / `remove(uuid)`. No business logic.
- `object XManager` — the single source of truth at runtime. `onInit()` loads the whole collection into in-memory maps; mutations touch the maps and mark ids in a `dirtyIds` set; a `ScheduledExecutor.scheduleAtFixedRate` job flushes only the dirty entries (islands: every 30s) via `updateAll`. Lookups go through the manager's maps, never through a fresh query.
- Managers with unsaved state expose `onDisable()` and **must be called explicitly** from `OceanBlockPlugin.onDisable()` — nothing wires this automatically, so a new stateful manager that isn't added there silently loses its last flush window. Every manager that buffers writes is listed there today; if you add one, add it there in the same commit. `battle-pass` (`ProgressManager`, `BattlePassManager`) is the exception that needs nothing: it writes through to Mongo on every mutation instead of buffering.
- The Kotlin `DataClassCodec` (bson-kotlin 5.1) **ignores constructor defaults**: a field missing from an old document decodes as `null` and a non-null parameter throws, failing the whole `toList()`. Adding a non-null field to a persisted data class needs a backfill in the repository `init` (`PlacedBlockRepository` sets `counters` with `updateMany(Filters.exists(..., false), Updates.set(...))`).
- A dirty-set flush must **clear the set only after the write succeeds**, and go through the repository's bulk `updateAll`/`saveAll` rather than one `update` per entry. Clearing first turns any Mongo hiccup into silent data loss — `IslandManager` had that bug.

#### Storing `ItemStack`s

`ItemStack` is not POJO-codec-friendly — **persist it as a Base64 `String`**, never as a nested object. `ItemSerializer` (`lib/item-builder`, `ocean_block.libs.item_builder`) wraps `BukkitObjectOutputStream` + Base64 for this; the auction house is the reference usage (`Auction` holds the item as `String`). Serialize at the model boundary (when the item enters/leaves the stored object), not inside repository read/write.
- `XxxSystem.init` calls `XManager.onInit()`. Systems that need a fully loaded world (e.g. `IslandsSystem`) defer it with `runTaskLater`.

### Textura plugin (`plugins/textura`)

Separate jar, hard `depend` of ocean-block, own `plugin.yml` via `plugin-yml`. It builds and serves the server resource pack at runtime using **team.unnamed `creative`**:

Source packages: `pack/` (pack assembly), `registry/` + `model/` (config parsing), `api/` (the only surface other plugins touch), `text/` (`TextMetrics`, pixel width + spacing components), `glyph/`, `http/`, `hud/`, `block/`, `menu/`, `command/`, `listener/`, `dialog/`. There is no `util/` — new code goes in the package that owns the concern.

- Registries (`GlyphRegistry`, `FontRegistry`, `TitleFontRegistry`, `ItemRegistry`, `BlockRegistry`) load YAML from `server/plugins/Textura/configs/{glyphs,fonts,items,blocks}` — mutable, so `/textura reload` re-reads them in place. `BlockRegistry` additionally indexes `OVERRIDE`-type entries by target block. Config ymls are **flat** inside each folder, named `<domain>[-<sub>].yml`; the registries recurse but subfolders only create a second way to do the same thing.
- `ResourcePackBuilder` orchestrates and delegates per domain to `FontPackWriter` / `ItemPackWriter` / `BlockPackWriter`; `PackBuilder` is the only class that talks to the creative API, and `PackAssets` maps a declared `caminho` to a file on disk plus its position in the zip. The zip is assembled **asynchronously** (guarded by an `AtomicBoolean`) into `generated/resourcepack.zip`; `PackHash.calculateSHA1` produces the hash. Either a local `ResourcePackServer` (Ktor-less mini HTTP server on `host.porta`, default 8080) serves it, or it is uploaded to LobFile when `host.lobfile.enabled` is set — the two paths are exclusive and both end by setting `packUrl` + hash. The LobFile key lives in `host.lobfile.api-key`; `TEXTURA_LOBFILE_API_KEY` overrides it when set.
- The data folder splits by lifetime: `configs/` (definitions) and `resource/` (assets, laid out exactly as the pack — the file's location *is* its key) are versioned; `data/` holds runtime state that must survive (`block-allocations.yml` — losing it changes the appearance of blocks already placed in the world); `generated/` and `external/` are gitignored. `server/plugins/Textura/README.md` documents every yml format and the reload/gerar flow — read it before touching a config.
- Other plugins consume it only through the `api/` objects (`GlyphApi`, `HudApi`, `ItemApi`, `BlockApi`, `TitleApi`/`TitleBuilder`, `TexturaTags`), which hold a `@Volatile` reference to the live registry so reloads propagate. Do not reach into `registry/` from outside.
- **The public API never exposes Kotlin types; both plugins shade their own Kotlin.** ocean-block and textura each carry a `kotlin.*` stdlib in their own plugin classloader, so any `kotlin.*` class in a public signature of `api/` or `hud/` (`Function0/1/2`, `Unit` as a type argument, `DefaultConstructorMarker`, an enum's `EnumEntries`, a companion's synthetic constructor) throws `LinkageError: loader constraint violation` the first time ocean-block calls it. Use Java functional types (`Supplier`, `IntSupplier`, `BooleanSupplier`, `Consumer`, `IntConsumer`) or Textura `fun interface`s (`DialogBindsConfig`, `DialogButtonAction`, `DialogListAction`); no default parameter values on public functions or constructors (write overloads or secondary constructors; a data class's generated `copy$default` is the one allowed exception); no companion objects on public API classes; enums that cross the boundary are Java enums in `src/main/java` (`DialogOpenResult`, `HudSide`). `PublicApiKotlinTypesTest` reflects over every public class of `api/` and `hud/` (plus `TitleFontSource`) and fails on any of this.
- `TitleApi` positions text by pixel inside GUI titles: each `y` becomes a generated `minecraft:font-ui-<y>` font in the pack. **A new `y` only exists after `/textura gerar`**, so register ascents early (`TitleApi.registerAscent(...)`, at system `init`) rather than the first time the menu opens. `TitleApi.source(path, baseAscent)` points a title at a custom font JSON (e.g. the digit-only `oneblock_level` font) so the `y` still means effective ascent.
- `TexturaTags` defines `<glyph:id>`, `<glyph:id:font>` and `<shift:n>`; both are self-closing and **never throw** — an unknown id renders empty rather than breaking the whole title. `Mini.mm` in `lib:formatter` is the MiniMessage instance carrying these resolvers.
- `dialog/` draws screens inside the vanilla dialog (design: `docs/superpowers/specs/2026-10-12-dialog-ui-json-design.md`): screens in `configs/ui/<id>.json`, themes in `configs/ui/*.yml`, art in `resource/assets/oneblock/textures/ui/`. `/textura gerar` writes the `oneblock:ui/*` fonts and publishes the `UiKit`; surfaces are pre-rendered per height (width is free at runtime) and sized icons per size (a `ui:` icon whose art is at least twice its size keeps up to 4x the pixels in its glyph, `IconScale.detail`, so a 128 px PNG shown at 32 stays sharp; `GlyphAdvance` rounds the advance like the client), so changing a panel height or icon size needs a regenerate. Clicks travel as `ClickEvent.custom(textura:ui, "<token>:<index>")` handled by `DialogOpener` (no per-render callbacks). `TranslationApi.translate(key)` returns the client translation (vanilla `en_us` + the `notificacoes.idioma` locale, default `pt_br`, plus a `resource/assets/minecraft/lang/<locale>.json` override) that the notifications load, so other plugins can show item names in Portuguese (null before the async load finishes). `DialogApi.refresh(player, id)` redraws the screen a player has open when it is that id (false otherwise), for live screens; the redraw issues new click tokens, so a click landing exactly on a refresh is dropped. Other plugins open screens only through `DialogApi.open(player, id) { binds -> binds.switch(...); binds.text(...); binds.button(key) { click -> } }` (Boolean) or `DialogApi.openResult(...)`, which returns `DialogOpenResult.Shown | NeedsPack | MissingScreen | Failed` (`NeedsPack`: Textura already showed its pack fallback or told the player; callers should only report `MissingScreen`/`Failed`). Repeated content: any node takes `"repeat": "<list>"` plus optional `"perPage": N` (max 64), fed by `list(key, Supplier<List<Map<String, String>>>)`, paged by `listPage(key, IntSupplier)`; a repeated `button`/`nav` with `bind` calls `listButton(bind, DialogListAction { click, index -> })` with the index in the full list. Slot `item`/`count`/`name`/`lore`, icons and flags take `{field}` from the entry. `/textura gerar` pre-renders every list-count combination (up to 512) and only bakes `item:` icons that code registered with `DialogApi.registerItemIcons(materials)` before the build. An `item:<name>` icon reads the vanilla client jar at `item/<name>`, then `block/<name>`, `_front`, `_side`, `_top` (`VanillaTextures`), so block items such as `loom` resolve. An item with no `item/<name>` texture whose material is a full occluding block (`Material.isOccluding`, checked inside `runCatching` so the offline Studio falls back to the flat face) is drawn as a 48 px cube by `BlockIcon.render(faces, 48)` with the vanilla GUI transform (rotation 30°/225°, scale 0.625, so it leaves the same margin as an inventory block; 48 px is exact at GUI scale 3; the old full-size squat cube looked wrong next to vanilla items) from `VanillaTextures.faces` (first animation frame of each face, grass top tinted green), like the inventory shows it; dialog icons keep up to 4x of that detail (`IconScale.detail`, now for `item:` icons too) and notifications get the same cube. Each click consumes its render token before the action runs, so a queued second click on the same render does nothing; the redraw issues new tokens. Textura ships `gui.vsh`/`gui.fsh` (from its jar, `src/main/resources/ui/`) that discard the opaque white focus outline vanilla draws around a clicked `plain_message` body (dialog widths 264 and 408, centred), trying GUI scales 1 to 8 because 26.3 may hand the GUI pipeline pixel coordinates. Multi-line tooltips are coloured per line after placeholders resolve (`∙` highlight, final `✔` green, `⌀`/`✖` red; see the README). Screens also accept the Studio editor's keys (pages + `nav`, `onClick` actions `[open] [page] [set] [message] [console] [player] [sound]`, `dropdown`, `slider`, `progress` (read-only bar: `track` + `fill` art, fill width `w * value / max`), text styles may name an extra bitmap font (`font: <name>` loads `configs/fonts/<name>.json`, written as `oneblock:ui/text_<name>_<offset>` and measured with its own widths; letter spacing comes from an alpha-1 column in each glyph), clicks on the previous render of the same session stay valid (`RenderState`) so a periodic `DialogApi.refresh` does not swallow clicks, the footer button (the default `gui.ok` one too) always reports the close so Esc ends the session, `pixels` (an image the code builds at open time, `binds.pixels(key, Supplier<BufferedImage>)`, drawn as one white glyph per run of equal pixels per row tinted by the text colour; `PixelRuns` splits rows into runs and power-of-two pieces and avoids the HUD marker reds, `UiPixels` glyphs for scales 1..4 and widths 1..64 are always in the pack, the Studio paints a checker or `PreviewRequest.pixels`), icon `states`, `{key?a:A|b:B}` / `%papi%` placeholders); control values are strings persisted per player in PDC (`textura:ui_<bind>`) unless code binds them, readable via `DialogApi.setting(player, key)`.

### Textura Studio (`tools/textura-studio`)

Local editor for the dialog screens, modelled on the resourcepack.ai Studio (spec: `docs/superpowers/specs/2026-10-19-textura-studio-base-design.md`). `./gradlew :tools:textura-studio:run` builds the React frontend in `web/` (npm) and serves everything on `http://127.0.0.1:7070` (`TEXTURA_DATA` overrides the data folder, `-Dstudio.port` the port, `-Dstudio.bind` or `STUDIO_BIND` the bind address, default `127.0.0.1`). The Kotlin backend reuses Textura's own `ScreenParser` → `ScreenCompiler` → `UiLayout` offline and paints the `LaidOut` with Java2D into a monitor-sized PNG (same slicing as `UiPackWriter`, fonts from `configs/fonts/custom.json`, vanilla dialog frame from the client jar in `generated/vanilla/`), so the preview matches the game. Saving writes `configs/ui/<id>.json` directly; the player still runs `/textura reload`. It never writes anything else in the server folder (glyph ymls are read with `YamlConfiguration`, not `GlyphRegistry`, which would rewrite them). `OfflineRegistryAccess` (registered via `META-INF/services`) exists only so `org.bukkit.Material` can initialise outside a server. Repeated lists preview with `perPage` empty entries (`{field}` shows literally) unless the editor sends sample entries (`lists`/`values` in `POST /api/preview`). Visual editing relies on an engine hook: `ScreenCompiler` tags every compiled `UiNode` with its `DefNode.path` and `UiLayout` returns a `PlacedBox(tag, x, y, w, h)` per tagged node in `LaidOut.boxes` (repeated instances get `path[index]`); the game ignores both. The frontend recomputes the same path labels (`name` or `<shape>#<index>`, joined by ` > `, page id as the first segment for page documents) in `web/src/editor/tree.ts` — keep the two in sync if the parser ever changes how it names nodes. Besides dialogs the Studio edits notification regions (`#/notificacoes`, preview in `render/HudPreview.kt` mirrors `LineGeometry` + `text.vsh` — the notify classes are `internal` to Textura, so the geometry is duplicated there and must follow any change to them), tests the HUD bossbar (`#/hud`), edits glyphs (`#/glyphs`) and themes (`#/temas`), and repaints block and item textures (`#/blocos`): `BlockCatalog` lists every block in `configs/blocks/*.yml`, every vanilla texture overridden under `resource/assets/minecraft/textures/block` (grouped by block, plus the non-minecraft textures referenced by an overriding model in `resource/assets/minecraft/models/block`, such as the Painel solar bottom) (one entry per declared face, `texture` as `all`) and every flat item of `configs/items/*.yml` whose texture is under `textures/item/`, the page shows a CSS cube and the faces, and `PixelEditor` paints pixel by pixel or uploads a PNG; `POST /api/blocks/texture` only writes a path that belongs to the catalog, 16×16 or the current size, up to 256, through `StudioFiles.writeImage`. After saving the player still runs `/textura gerar` (or restarts). `StudioFiles` is the only writer: a path whitelist (`configs/{hud,glyphs,ui}/*.yml`, `resource/assets/**.png` and `.png.slice`) that keeps `config.yml` (LobFile key) unreachable.

### Design docs

Feature designs written before implementation live in `docs/superpowers/specs/<date>-<feature>-design.md` (custom-item framework, island settings, glyph spritesheet, textura port, oneblock progression, OceanBlock fork); the step-by-step implementation plans derived from them live in `docs/superpowers/plans/<date>-<feature>.md`. Check for an existing spec before designing a feature from scratch, and keep new specs/plans in those folders with the same naming. `.superpowers/sdd/` holds throwaway agent run artifacts — not documentation, and its `baseline-task` module is not in `settings.gradle.kts`.

## Conventions

- **Do not write comments in code.** No KDoc, no inline notes, no "why" blocks — not in Kotlin, not in Gradle scripts, not in YAML you generate. Name things well and let the code stand alone. This overrides any habit of explaining reasoning in-file: put the explanation in the chat response instead. Only exception: a comment the user explicitly asks for, or one that already exists and you are editing around.
- User-facing strings are in **Portuguese**; keep that when editing nearby code. Pre-existing comments are also in Portuguese — leave them as they are, don't translate or extend them.
- Commits follow `type(scope): description` (`feat`, `fix`, `refactor`, `docs`, `chore`) — see `git log`.
